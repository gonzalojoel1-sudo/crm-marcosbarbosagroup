## Sanity check del presupuesto RAM

| Consumidor | Estimación realista | Límite del spec | Comentario |
|---|---|---|---|
| mariadb | ~650–750 MB (buffer 512M + overhead) | 1g | OK |
| backend (2×gunicorn) | ~380–450 MB idle-warm; picos >500 MB en migraciones/exports | 512m | Justo; OOM del backend posible en operación pesada. Aceptable documentado, o subir a 640m. |
| worker (1) | ~150–250 MB | 400m | OK |
| scheduler | ~120–200 MB | 400m | OK (holgado) |
| websocket | ~80–120 MB (2 usuarios) | 192m | OK |
| frontend (nginx) | ~10–20 MB | 64m | OK |
| redis ×2 | cache ~150 MB (128+overhead) + queue ~110 MB ≈ 260 MB | 160m ×2 | OK **solo si** 160m es por contenedor (aclarar, M2) |
| configurator | 0 (one-shot) | — | — |
| **Total real** | **≈ 1.75–1.95 GB** | — | vs ~1.8 GB disponibles → **headroom ≈ 0 a −150 MB**, no los ~100 MB del spec |

**Veredicto:** la matemática del spec es ~10% optimista pero **viable con el swap de 4 GB** para 2 usuarios. La suma de límites (2.9 GB) excede la RAM disponible — correcto como red de seguridad (los límites son techos, no reservas), implica que el OOM-killer actuará bajo presión extrema; el límite de backend es el más ajustado. Concreto: sin el falso ahorro de perf-schema (que no contaban como RAM extra) el presupuesto no cambia; solo la redacción del headroom.

## Lo que falta en el spec (trampas para el implementador)

1. **Cómo entra `crm` al bench** (resuelve S1): elegir (a) imagen extendida con apps.json `[frappe branch-15, crm main]` vía frappe_docker build, o (b) `ghcr.io/frappe/crm:stable` oficial. Un one-shot `bench get-app crm` dentro del contenedor NO sobrevive recreaciones (apps/ es imagen-local, el volumen es solo sites/) — descartarlo.
2. **Propagación del password root de MariaDB:** pwd.yml pasa `MARIADB_ROOT_PASSWORD` a `db` **y** a `backend`; el `new-site` lo necesita vía `--db-root-password`. El `.env` del spec solo lista `DB_PASSWORD` — distinguir root vs site-db-password.
3. **`--mariadb-user-host-login-scope='%'`** en el `new-site` (DB en contenedor separado; el propio código de v15 lo recomienda en ese escenario).
4. **Espera/healthcheck de dependencias:** pwd.yml usa `wait-for-it db:3306 redis-cache redis-queue` + espera el `common_site_config.json` del configurator antes del `new-site`. El spec no menciona el timing (configurator debe completarse antes de backend/worker/scheduler/websocket: `depends_on: service_completed_successfully`).
5. **Healthcheck de MariaDB:** existe `healthcheck.sh --connect --innodb_initialized` en la imagen oficial mariadb:10.6 — incluirlo para orquestar el new-site.
6. **Nombre del site = dominio:** el compose oficial usa `FRAPPE_SITE_NAME_HEADER: $$host` → el site DEBE llamarse exactamente `crm.marcosbarbosagroup.com` (el spec lo hace; explicitarlo como requisito).
7. **Volumen de datos para redis-queue** (`redis-queue-data:/data`): el spec lista solo mariadb-data/sites/logs; sin él, jobs pendientes se pierden en recreaciones.
8. **Red de Traefik/Dokploy hacia `crm-net`:** Traefik debe estar attachado a la red del compose (o Dokploy lo maneja via su proxy); decidir labels vs UI de dominios y anotarlo.
9. **`notes` no es campo de CRM Lead** (M4): mapping fase 2 → `FCRM Note` o drop.
